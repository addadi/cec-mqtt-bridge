# Incident postmortem: cec-mqtt-bridge outage (fixed 2026-11-21)

## Summary

The `cec-mqtt-bridge.service` (highly needed by Home Assistant automations on
`homeassistant.brahms`) crash-looped with `TypeError: Unsupported callback API
version` every ~10 s. Detected via the mozart host-ops agent (journal restart
counter > 4000). Fixed and verified live at **2026-11-21 10:34:23 IST**.

## Root cause chain

1. **System `paho-mqtt` upgraded 1.x → 2.x** on mozart (python 3.14 system
   site-packages, `/usr/lib/python3.14/site-packages/paho`). paho 2.x refuses
   `mqtt.Client(client_id)` without a `callback_api_version` argument.
2. **Rotten hybrid runtime**: the unit's `ExecStart` ran
   `~/.local/bin/cec-mqtt-bridge`, a pip `--user` entry script with shebang
   `#!/usr/bin/python` → **python 3.14**, so `paho` resolved to the system 2.2.0.
3. But the unit also set `PYTHONPATH=/home/addadi/.local/lib/python3.13/site-packages`,
   so the **bridge module itself** came from a stale python 3.13 `--user` install
   while its dependencies came from 3.14 system packages — the crash import stack
   proves the mix (bridge.py from 3.13 user dir, paho from 3.14 system dir).
4. `bridge.py` used the paho 1.x callback API → instant `TypeError` in
   `Bridge.__init__` → exit 1 → `Restart=always` (RestartSec=10) → infinite loop.

**Why the "quick pin" (`pip install --user 'paho-mqtt<2'`) would NOT have worked**:
`pip --user` installs into python **3.13** site-packages, but the interpreter
executing the entry script was **3.14**. The pin would never be imported. The
python 3.13 `--user` install was already partially stale (no paho at all for
3.13 at fix time).

## Fix (commits 4ea4ed0, 6169f72, b937012)

- **Code**: migrated `src/cec_mqtt_bridge/bridge.py` to the paho-mqtt 2.x
  callback API: `mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=...)`,
  new `on_connect(client, userdata, connect_flags, reason_code, properties)` and
  `on_disconnect(...)` signatures, `reconnect_delay_set(1, 60)` for broker
  reconnect backoff, CEC adapter open retry (6 × 10 s, covers boot-time
  contention e.g. Kodi), and a clean retained `bridge/status=offline` publish
  before shutdown.
- **Deployment**: dedicated venv `~/venvs/cec-mqtt-bridge`
  (python 3.14, `--system-site-packages` so the distro libcec `cec` module
  resolves; `paho-mqtt` 2.2.0; repo installed **editable**). The user-owned
  launcher `~/.local/bin/cec-mqtt-bridge` was replaced with a shim that
  `exec env -u PYTHONPATH ~/venvs/cec-mqtt-bridge/bin/cec-mqtt-bridge "$@"` —
  the stale 3.13 user site-packages can never shadow again.
- **Reload without sudo**: killed the process; `Restart=always` revived the
  service onto the new code (live `/etc/systemd/system/cec-mqtt-bridge.service`
  was never touched).

## Verification evidence

- `systemctl status`: `active (running)` since 10:34:23 IST, zero restarts after.
- `/proc/<pid>/cmdline` shows the venv interpreter, no PYTHONPATH shadowing.
- Broker subscription test against `homeassistant.brahms:1883` (config creds)
  received retained `media/bridge/status=online` plus the full device tree:
  TV (0), OSMC recorder (1), Denon AVR (3/5), `cec/audio/volume`, `cec/audio/mute`,
  live `cec/rx` traffic — HA automations see `media/...` topics again.
- CEC adapter open on port `Linux`, logical address 1 (`Connected to HDMI-CEC
  with ID 1` in journal).
